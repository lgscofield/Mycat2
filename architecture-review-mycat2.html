网络模型 A：Native NIO Reactor

模式：手写 Java NIO Reactor，非 Netty

Accept：1 个 NIOAcceptor 专用线程

Reactor：N 个 MycatReactorThread，Selector.select() 事件循环

分配：ThreadLocalRandom 随机分配连接

任务传递：ConcurrentLinkedQueue + selector.wakeup()

Buffer：每 Reactor 线程独立 ReactorBufferPool

防护：epoll 空轮询检测与 rebuildSelector

网络模型 B：Vert.x (生产入口)

入口：MycatCore.main() → VertxMycatServer

底层：Vert.x NetServer (基于 Netty)

Event Loop：reactorNumber 个事件循环

Worker Pool：maxPoolSize 个 worker 线程

协议处理：VertxMySQLAuthHandler 认证

异步模型：Future/Promise + RxJava Observable

Verticle：多实例部署，每个 Verticle 一个 Server

二、核心优势与亮点

★ 亮点

深度 Calcite 集成的查询优化器

定制完整 TypeSystem、100+ MySQL 函数算子、35+ 优化规则和 MycatConvention 物理约定。RBO+CBO 两阶段优化管线在开源中间件中属顶级水准，支持 Partition Key Join、Merge Join、BKA Join 等分布式特有优化。

★ 亮点

极其丰富的分片算法生态

26+ 分片算法覆盖 Hash、Range、时间枚举、字符串映射等全场景。AutoFunction 支持 dbNum × tableNum 二维分片，独立配置 db/table 分片函数。完全兼容 Mycat 1.x 算法，迁移成本为零。

★ 亮点

Arrow 向量化执行引擎

基于 Apache Arrow 的列式向量化执行引擎，35+ 物理算子覆盖 Scan/Join/Aggregate/Sort/TopN/Union 全场景。VectorSchemaRoot 批式流转，减少虚方法调用和内存分配开销。

★ 亮点

完整的 XA 两阶段提交实现

生产级 XA 支持：完整状态机、WAL 日志（File/Memory/KV 三种 Repository）、崩溃恢复（XA RECOVER + 延迟重试）、One-Phase 单阶段优化。中间件领域完整度最高的 XA 实现之一。

★ 亮点

多数据库方言透明代理

通过 Druid Parser + jOOQ DSL 方言翻译，前端 MySQL 协议可透明代理到 MySQL、PostgreSQL、Oracle、SQL Server、ClickHouse 等多种后端，对业务层完全屏蔽差异。

★ 亮点

HBT 查询语言 — 可调试的执行计划 DSL

自研 HBT (Hint-Based Template) 中间表示，支持文本序列化/反序列化。开发者可通过 EXPLAIN 查看可读计划，也可通过 Hint 直接指定模板覆盖优化器决策。

三、架构缺陷与系统级不足

仅聚焦宏观系统架构与中间件核心能力，忽略代码风格与局部坏味道

▲ 严重

双网络栈并行维护导致架构撕裂

现状 (Before)

Native NIO Reactor
← 完整实现，非生产入口
Vert.x NetServer
← 实际生产入口
两套独立的协议编解码、Session 管理、连接处理

影响

  • • 接缝泄漏：MySQL 协议编解码在两套栈中各自实现，功能重叠
  • • 维护负担倍增：协议层 bug 需修复两处，行为一致性无法保证
  • • 测试分散：同一语义功能需两套测试覆盖
▲ 严重

双执行引擎缺乏统一调度接缝

影响

  • • 调度不统一：两个引擎独立运行，无统一资源调度器
  • • 优化器盲区：CBO 代价模型无法跨引擎比较
  • • 执行计划断裂：查询可能跨引擎切换，增加调试复杂度
▲ 中等

后端连接模型与前端异步模型断裂

前端使用 Vert.x 全异步 Event Loop，但后端数据源依赖 Druid 连接池（JDBC 阻塞模型）。JDBC 调用在 Worker Pool 中执行，每个后端查询需一次线程切换。高并发下 Worker Pool 成为瓶颈。

▲ 中等

缺乏完善的分布式查询取消机制

客户端断开或超时时，跨多个后端分片的查询缺乏端到端取消传播。RxJava Observable 的 dispose 机制未系统性贯穿所有物理算子和后端连接，可能导致后端继续执行已无效查询。

▲ 中等

元数据管理缺乏版本化与一致性保障

MetadataManager 以内存 Map 管理 Schema 元数据，DDL 变更直接修改内存状态，缺乏版本号、原子快照和并发安全的变更传播。DDL 与 DML 并发时可能出现执行计划基于过期元数据编译。

▲ 中等

缺乏连接级别的背压与流量控制

缺少从后端结果集生产速率到前端客户端消费速率的端到端背压机制。客户端消费慢时可能持续拉取数据导致 OOM。FULL_TABLE_SCAN_LIMIT (1024) 作为粗糙限制无法替代精细流控。

结合 Virtual Threads、Structured Concurrency、Generational ZGC、Pattern Matching 等关键特性

Virtual Threads 重构后端连接并发模型

当前痛点

前端 Vert.x 异步模型 + 后端 JDBC 阻塞式连接。每个后端查询需在 Worker Pool 线程执行 JDBC。Worker Pool 线程数有限（maxPoolSize），高并发时成为瓶颈。Event Loop 被慢查询拖慢时影响所有连接。

Before: Worker Pool 瓶颈

→ 非阻塞 I/O
Event Loop N
→ 非阻塞 I/O

JDBC 阻塞
Worker 2
JDBC 阻塞

JDBC 阻塞 (maxPoolSize 瓶颈)
M 远小于 N，Worker Pool 是吞吐天花板

After: Virtual Threads 每连接一线程

Event Loop
→ 接受连接 + 协议解析
VThread 1
JDBC 阻塞时自动让出 carrier
VThread 2

VThread N
与平台线程 1:1 映射
Worker Pool 消除，JDBC 阻塞不消耗 OS 线程

具体演进路径

  1. 将 DruidDatasourceProvider 的 JDBC 调用从 Worker Pool 迁移到 Executors.newVirtualThreadPerTaskExecutor()
  2. 为每个入站 SQL 查询分配虚拟线程，线程内同步执行：路由计算 → 获取连接 → JDBC execute → 结果集处理
  3. Virtual Thread 在 JDBC 阻塞时自动 unmount carrier 线程，ForkJoinPool carrier 立即服务其他虚拟线程
  4. 渐进式迁移：先在 VertxExecuter 中将 executeBlocking() 替换为虚拟线程提交
  5. 预期收益：Worker Pool 瓶颈消除，吞吐提升 3-10x，长尾延迟降低 50%+

具体演进路径

  1. 在 VertxExecuter 的分片查询中使用 StructuredTaskScope.ShutdownOnFailure 替代 CompositeFuture.all()
  2. 每个分片 SQL 执行作为 subtask fork 到 scope，任一失败自动 shutdown 兄弟任务
  3. 配合 Virtual Thread，每个 subtask 运行在虚拟线程，scope.join() 阻塞成本极低
  4. 对 Merge Sort、Hash Join 等多路汇聚算子，使用 ShutdownOnSuccess 实现 early-exit
  5. 预期收益：消除孤儿查询，资源泄漏风险归零，取消语义端到端保障
◆ 核心演进 Worth exploring

Generational ZGC 优化 GC 停顿与内存效率

当前 GC 痛点

短生命周期对象洪泛

每个查询产生大量临时对象：Druid AST、Calcite SqlNode/RelNode、Arrow VectorSchemaRoot

Buffer 池内存碎片

ReactorBufferPool 长生命周期对象与短命对象混合在老年代，Full GC 频率升高

长尾延迟不可控

JDK 8 G1/CMS 在高并发下百毫秒级 STW 停顿，直接影响 P99 延迟

Generational ZGC 演进路径

  1. 启用 -XX:+UseZGC -XX:+ZGenerational，分代 ZGC 将堆分为年轻代/老年代，年轻代 GC 停顿 < 1ms
  2. SQL 解析/优化短生命周期对象在年轻代快速回收，连接池/Buffer 池长生命周期对象在老年代极少触发 GC
  3. Arrow off-heap 内存不受 ZGC 管理，但 ZGC colored pointer 元数据开销更小，整体堆占用降低
  4. 配合 -XX:SoftMaxHeapSize 软限制控制堆增长，避免容器 OOMKill
  5. 预期收益：P99 延迟从百毫秒降至亚毫秒（GC 停顿），年轻代 GC 吞吐提升 2-3x，堆利用率提高 20-30%
◆ 核心演进 Worth exploring

Pattern Matching 重构 SQL AST 处理与协议解析

当前痛点

大量 instanceof + 类型强转的 AST 遍历和报文分发代码。MycatCalciteMySqlNodeVisitor 单文件 96.8KB，MySQLPacketResolver 基于首字节 if-else 识别报文类型。新增节点需修改大量分支。

Pattern Matching 演进路径

  1. Pattern Matching for instanceof：消除 AST 遍历中的显式强转，减少 30%+ 样板代码
  2. Sealed Classes + Switch Pattern Matching：HBT AST 节点声明为 sealed interface，switch 获得穷举检查
  3. Record Patterns：ShardingFunction 配置解构，直接提取 dbNum/tableMethod 等字段
  4. MySQL 协议报文用 sealed interface 定义 ADT，switch pattern 替代 if-else 链
  5. 预期收益：AST 处理可读性和正确性大幅提升，编译器保障穷举性，新增 SQL 支持改动面积缩小
◆ 核心演进 Strong

JDK 21 + Virtual Threads 统一双网络栈

Before: 双栈并行

Native NIO Reactor — 手写 Selector 事件循环，维护成本高
Vert.x NetServer — 与 Vert.x 深度耦合的生产入口
两套独立 MySQL 协议编解码，行为一致性无法保证

After: 统一网络栈

保留 Vert.x NetServer 为唯一入口（或评估 JDK 21 SocketChannel + Virtual Thread）
统一协议编解码为单一 module，一个接缝(Seam)，两套 adapter（生产/测试）
删除 Native NIO Reactor 代码，减少 40%+ 维护负担
◆ 核心演进 Speculative

Scoped Values 替代 ThreadLocal 传递查询上下文

演进路径

  1. 当前 ThreadLocal 传递查询上下文（DataContext、事务状态），Virtual Thread 下 ThreadLocal 性能开销和泄漏风险增大
  2. JDK 21 Scoped Values 提供不可变、有界生命周期的上下文传递，天然适配虚拟线程
  3. 将查询上下文（Schema、User、Transaction、Trace ID）封装为 record，通过 ScopedValue 在 StructuredTaskScope 中传递
  4. 预期收益：消除 ThreadLocal 泄漏，虚拟线程间上下文零拷贝，调试可追溯
