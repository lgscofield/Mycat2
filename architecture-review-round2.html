维度一：模块重新设计

识别并加深浅层模块，建立清晰的接缝（seam）和适配器（adapter）策略

Strong

1.1 废弃 Native NIO 栈，统一 Vert.x 网络入口

涉及文件：

  • proxy/src/main/java/io/mycat/NativeMycatServer.java
  • proxy/src/main/java/io/mycat/proxy/ (50+ 文件)
  • proxy/src/main/java/io/mycat/proxy/reactor/ (4 文件)
  • proxy/src/main/java/io/mycat/proxy/session/ (5 文件)
  • proxy/src/main/java/io/mycat/proxy/handler/ (12 文件)

问题：

MycatCore 硬编码使用 VertxMycatServer，NativeMycatServer 仅在测试中通过系统属性切换。两套完全独立的 MySQL 协议编解码、Session 管理、连接池实现，共享代码仅有 MycatServer 和 MycatDataContext 接口。proxy 模块 50+ 文件的 NIO 代码在生产中从不执行。

方案：

  1. 将 proxy 模块标记为 @Deprecated，保留一个版本周期后移除
  2. 将 NativeMycatServer 中有价值的功能（如 CommandDispatcher 接口的完整实现）移植到 Vert.x 栈
  3. VertxMycatServer 中 4 个返回 "unsupported" 的监控方法需要补充实现
  4. Native 连接池 MySQLDatasourcePool 的 NIO 心跳机制可作为参考用于优化 JDBC 心跳

收益（Leverage & Locality）：

  • Locality：消除 50+ 文件的双栈维护成本，所有网络层修改集中在一处
  • Leverage：单栈实现使测试覆盖更聚焦，运维监控接口完整可用
  • 删除测试：删除 Native 栈后，复杂度不会分散到调用者——因为调用者本就不使用它
Strong

1.2 统一执行引擎接缝：修复断裂的 Calcite→Arrow 编译管线

涉及文件：

  • executor/.../MycatCalciteCompiler.java（353行全注释）
  • executor/.../CalciteCompiler.java（builder 包下，实际使用）
  • mycat2/.../ExecutorProviderImpl.java
  • hbt/.../ExecutorProvider.java（接口定义）

问题：

存在两条执行路径：① Arrow 向量引擎（36 个 PhysicalPlan 算子）；② Calcite Enumerable 代码生成（Janino 运行时编译）。关键问题是 MycatCalciteCompiler（RelNode→PhysicalPlan 的桥接器）整个被注释掉，Arrow 引擎的 Calcite 编译路径完全断裂。当前实际走的是 Calcite Enumerable 代码生成路径。

方案：

  1. 在 hbt 模块定义 ExecutionDispatcher 接口作为执行策略的统一接缝
  2. 修复 CalciteCompiler（builder 包下），使其成为 RelNode → Arrow PhysicalPlan 的可靠编译器
  3. 明确三种执行策略的适用场景：向量化（复杂聚合/Join）、透传（简单 CRUD）、代码生成（兼容遗留）
  4. 删除被注释的 MycatCalciteCompiler 或恢复其功能

收益：

  • 深度（Depth）：ExecutionDispatcher 接缝背后隐藏着复杂的执行策略选择逻辑，调用者只需传入 RelNode
  • 可测试性：每种执行策略可独立 mock 和测试
Strong

1.3 深化 Datasource SPI：修复抽象泄漏

❌ Before：抽象泄漏

JdbcDataSource.isValid() → 始终返回 false → 空闲连接心跳永远失败
JdbcDataSource.close() → 反射查找 close() 方法 → 类型不安全
JdbcConnectionManager → switch(dbType) "mongodb" 特殊分支 → 破坏统一抽象
DruidDatasourceProvider → 直接暴露 DruidDataSource API → SPI 泄漏

✓ After：深层 SPI 模块

DatasourceProvider（深层接口）→ create / close / validate / healthCheck
HikariCPDatasourceProvider（适配器）→ 隐藏 HikariCP 细节
ConnectionHealthMonitor（内部接缝）→ 统一心跳/健康检查策略
DbTypeStrategy（策略接缝）→ 各数据库方言差异处理外置

方案：

  1. 修复 JdbcDataSource.isValid()：实际检查连接有效性（Connection.isValid(3)）
  2. 扩展 DatasourceProvider 接口：增加 validate()、healthCheck() 方法
  3. 消除 JdbcConnectionManager 中的 MongoDB switch 分支：通过 DbTypeStrategy 策略模式外置
  4. 用 HikariCP 替换 Druid 连接池（详见维度四决策矩阵 4.3）
  5. 消除 JdbcDataSource.close() 的反射调用：DatasourceProvider 契约中明确 close 语义
Worth exploring

1.4 清理 Proxy 模块：提取 CommandDispatcher 为独立接缝

问题：proxy 模块混合了三个不同职责：① NIO Reactor 线程管理；② MySQL 协议编解码；③ 命令分发与处理。其中 CommandDispatcher 接口（命令分发契约）是唯一可跨网络栈复用的深层接缝，但被 NIO 基础设施紧密包裹。

方案：将 CommandDispatcher 及相关命令处理逻辑提取到独立的 command 模块中，使其成为前端协议层与后端执行层之间的清晰接缝。Vert.x 栈的 MycatVertxMySQLHandler 和 NIO 栈的 CommandResolver 都成为该接缝的适配器。

删除测试：如果删除 CommandDispatcher 模块，命令处理的复杂度会分散到每个网络栈各自的 handler 中——说明它是一个有价值的深层模块。

3.3 Druid 使用模式优化（无 Fork 需模块化）

发现：经代码验证，项目中不存在 Druid 包级别的 Fork 代码（com.alibaba.druid.* 包下无自定义类）。之前报告中提到的 "MycatSQLUtils" 等实际位于 io.mycat 包下，仅使用了 Druid 的公开 API。

执行时间：Phase 1 标记 @Deprecated → Phase 2 移植有价值逻辑 → Phase 3 移除

4.2 RxJava 3 vs Vert.x Future 异步模型

现状数据：

  • RxJava 3：~15 个活跃文件（executor 物理计划、swapbuffer、hbt 查询执行）
  • Vert.x Future/Promise：~40+ 活跃文件（事务管理、连接池、XA 协议、DML 操作）
  • CompletableFuture：仅 2 处（临时桥梁）
  • 3 个完整类被注释掉（FutureNewMycatConnectionImpl, NewVertxConnectionImpl, NewMariadbConnectionImpl），共 1200+ 行 — 证明曾尝试迁移到纯 Future 但放弃

🔴 核心痛点：NewMycatConnection 接口同时暴露 Observable 和 Future

// 同一个接口中两种异步模型并存
Observable<VectorSchemaRoot> query(String sql);
Future<RowBaseIterator> prepareQuery(String sql, List params);

导致实现类内部出现 Observable.create(Future.transform(...)) 的嵌套反模式。

评估维度RxJava 3Vert.x FutureJDK 21 Virtual Threads
当前使用广度15 文件40+ 文件0（未引入）
背压（Backpressure）原生支持不支持不适用
流式数据处理Observable 链式操作Future 无流式语义Iterator + Virtual Thread
简单异步编排过重轻量直观同步写法
JDK 21 兼容性线程池与 VT 冲突Vert.x 4.5+ 支持原生
学习曲线陡峭平缓最简单
执行引擎适配PhysicalPlan.execute()需重新设计可简化为同步

🏆 最终决策：分层策略 — 执行引擎保留 RxJava，I/O 层统一 Vert.x Future，长期向 Virtual Threads 演进

  1. 执行引擎层（PhysicalPlan）：保留 Observable<VectorSchemaRoot>，因为背压和流式数据处理是 RxJava 的核心优势，且 36 个物理算子的改动成本极高
  2. I/O 与连接管理层：统一使用 Vert.x Future，消除 RxJava 在非执行引擎代码中的使用
  3. 接缝处转换：在 ExecutionDispatcher 接缝处提供 Observable ↔ Future 的标准转换器
  4. JDK 21 长期演进：Virtual Threads + Structured Concurrency 最终可替代 RxJava 的流式处理，但需要先完成 JDK 升级（Phase 3+）

SQL 防火墙内置 WallFilter无
MyCat2 实际使用仅使用基础连接池功能—
SPI 切换成本—低（DatasourceProvider 接口已存在）
社区活跃度维护模式Spring Boot 默认选择
配置复杂度50+ 配置项~15 核心配置项

🏆 最终决策：替换为 HikariCP 5.x，保留 Druid SQL Parser

理由：

  • Mycat2 仅使用 Druid 的基础连接池功能，StatFilter/WallFilter 均未启用
  • Druid Pool 的 synchronized 锁机制是 JDK 21 Virtual Threads 的硬性阻碍
  • 项目已有 DatasourceProvider SPI 接口 + 反射加载机制，切换成本极低
  • HikariCP 已在 pom.xml 中声明（3.3.1/3.4.5），只是未被启用

迁移路径：

  1. 创建 HikariCPDatasourceProvider implements DatasourceProvider
  2. 配置文件中 provider 类名从 DruidDatasourceProvider 改为 HikariCPDatasourceProvider
  3. 映射 Druid 配置项到 HikariCP 等价项（maximumPoolSize, minimumIdle 等）
  4. 保留 DruidDatasourceProvider 作为备选（用户可通过配置切换）
  5. 验证心跳、连接有效性检查（修复 isValid() bug）在新 Provider 中的正确性
