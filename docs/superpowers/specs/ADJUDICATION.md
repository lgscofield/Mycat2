# 兼容性最终裁定依据（对拍基准）

> **目的**：终结"Mycat 应该怎么做"靠口头推理反复改口的老问题。凡涉及"对不对 / 该怎么做"的兼容性判断，一律按本文件的优先级裁定；不附本文件要求的证据，结论视为**待验假设**，不得作数。

## 支持范围

仅 **MySQL** 与 **MariaDB** 各 persona 版本。与 Oracle 等其它数据库无关（历史讨论中"oracle"一词系测试术语"对拍基准/真值基准"的误用，此后不再使用）。

## 四级裁定依据（优先级从高到低）

1. **真 MySQL / MariaDB 对应 persona 版本的实测 wire 行为** —— 字节级**终审**，不可被口头曲解。
   每次实测须抓四样：① 结果行 ② **列头五元组**（Type / Collation / Length / Decimals / Flags）③ `SHOW WARNINGS` ④ 错误码 / SQLSTATE。
2. **对应版本官网文档** —— **规则层第一权威**：定义"规则应当是什么"、覆盖第⑴级测不到的情形、解释实测现象、并在⑴⑵冲突时用来判断"是 server 的 bug 还是我方配错"。
3. **DEBT-QUEUE / 记忆 / commit 自述等既有记录** —— **仅作检索线索，永不当证据**（对齐"不信旧记录，当前证据复核"原则）。
4. **我的推理** —— **只能产假设**，必须回⑴⑵验证后才作数。

## 文档 ↔ 实测冲突的处理（不硬选）

二者冲突本身是一个**要挂账的发现**（可能是某版 server 行为不合文档，或文档滞后）。不擅自"挑一个信"；记入留痕，按"**客户端实际连到这台 server 会拿到什么**"来定代理应当模仿谁——因为无缝替换的成败最终由客户端收到的字节决定，而客户端吃字节、不吃文档。

## 证据要求（下任何兼容性结论必须附）

- 实测：来自哪台 server（镜像 tag，**实测前先 `docker` 核验版本**）、命令原文与输出。
- 引文档：给出版本与来源链接。
- 无⑴⑵支撑的判断：显式标注"假设，待验"。

## 为何以实测为终审（本轮案例）

`SELECT b'11111111' UNION ALL SELECT 123`（BIT ∪ BIGINT），三版后端归并出的列类型互异（均为实测）：

| 后端 | Type | Collation | Length | Decimals |
|---|---|---|---|---|
| MySQL 8.0 | VAR_STRING | binary (63) | 4 | 0 |
| MySQL 5.7 | VAR_STRING | latin1_swedish_ci (8) | 6 | 31 |
| MariaDB 10.11 | VAR_STRING | binary (63) | 3 | 39 |

文档只会说"union 会做类型归并"这种**规则**，但具体 charset/长度/小数位是**实现事实**，文档基本不精确给，只有对应版本服务器知道。代理哪怕"照文档的意思"给出合理类型，只要这些字节级细节与目标版本不符，某些 connector 照样取错值或崩——故字节级无缝替换须匹配**对应版本实测**。

## 操作机制（对拍基准 harness）

同一条 SQL **分别**喂给 ①直连后端（版本 V）与 ②经 Mycat（persona 配成 V），逐字段比对上述四样：**一致 = 对；有差 = bug，且自动带上"期望值(后端给的) vs 实际值(Mycat 给的)"**。
基座复用现成的 `run-matrix` / `CrudResultMatrixTest` / ×7 版本矩阵 infra，扩展点：从"只比行值"扩到"比列头五元组 + warnings + 错误码"。
